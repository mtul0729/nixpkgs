# The mtul0729/nixpkgs fork

This fork is, first, the home of the packages I maintain myself, and only second a
staging area for upstream pull requests. A branch here is a long-lived asset, not
something expected to disappear once a PR is merged.

## Shape

`master` is always based on upstream `nixos-unstable` and holds only CI files and
documentation — never package code. It may carry more than one commit; CI rebases the
whole stack onto the current `nixos-unstable` every hour. It contains only:

- `.github/workflows/{ci-check,update,integrate}.yml` — the only enabled workflows;
  every upstream workflow has been disabled by hand
- `nixpkgs-ci/` — the branch list and this document

Every package lives on its own topic branch, cut from upstream `nixos-unstable`, adding or
changing only `pkgs/by-name/<shard>/<name>/`. `integration` is generated by CI:
upstream `nixos-unstable` with each topic branch rebased on top. Consumers take a single input,
`github:mtul0729/nixpkgs/integration`, so cache hits are per-derivation and nothing has
to be re-wired when a package is added.

Everything here is based on upstream `nixos-unstable` rather than `master`. The
systems consuming this fork run unstable, so `integration` sits on the same
commit the official binary cache was built against; basing it on `master` would
produce a second set of derivations for identical versions and miss every cache entry.

`nixpkgs-ci/branches.txt` is the single source of truth for which branches carry
packages. Adding a branch means editing that file; CI reads nothing else.

every job is based on it. The one remaining reason to look at upstream `master` is when
preparing a pull request against nixpkgs, to check whether a change already landed there.

## CI

Three workflows, each with one job:

| workflow | trigger | what it does |
| --- | --- | --- |
| `ci-check` | push to `master` touching `nixpkgs-ci/**` or `.github/workflows/**` | parses every workflow's YAML, checks `branches.txt` syntax, and checks that each branch exists on the fork |
| `update` | hourly at `:13`, manual (`only`, `verify_only`) | per branch: `nix-update`, IFD check, build, and only then push the branch |
| `integrate` | after `update` finishes, hourly at `:43`, manual | rebase every branch onto current `nixos-unstable`, push `integration`, build the attributes the branches carry |

A docs-only push to `master` costs `ci-check` (~15 s) and nothing else.

### update

One matrix leg per branch, and a leg does **upgrade → verify → push** in the same
workspace, so a branch never receives a commit that has not been built:

1. `nix-update -u <pkg> --format` — a package opts in by declaring `passthru.updateScript`;
2. `nix-instantiate --option allow-import-from-derivation false -A <pkg>.drvPath`, the same
   IFD check `pkgs/README.md` asks for;
3. `nix-build -A <pkg>` inside `cachix watch-exec mtul`, so the result lands in the cache;
4. only then `git commit` and `git push`.

If the build fails, nothing is committed. To keep a broken version from being retried
every hour, the leg pushes a `ci-failed/<branch>/<tree>` tag; the next run computes the
same tree, sees the tag, and skips. Touch the package — or a new version appears — and
the tree changes, so it retries on its own. A successful update deletes that branch's
tags.

`-f only=pkg/helix` limits a run to those branches. `-f verify_only=true` skips
`nix-update` and only runs the two checks: that is the fast loop after a manual fix.

### integrate

`integrate` rebases every branch onto the current `nixos-unstable`, pushes `integration`,
then runs `nix-build` for the attributes those branches declare (`branches.txt`'s
explicit list first, otherwise the by-name directory names).

That build is the drift check. Each branch was verified against **its own** base, while
`integration` is built against **today's** unstable: if upstream moved a dependency, the
derivation changes and gets rebuilt here, and a package that no longer builds turns the
run red. When nothing changed it is a pure download.

A branch that fails to rebase is skipped and named in the error; the others are still
published.
## Adding a package

1. Create a branch from upstream `nixos-unstable` and add `pkgs/by-name/<shard>/<name>/package.nix`.
2. Declare `passthru.updateScript` unless you want to pin it manually.
3. Make sure evaluation does not require import-from-derivation (see below).
4. Check it locally — these commands catch what CI would reject:

   ```bash
   nix-instantiate --eval --strict --option allow-import-from-derivation false -A <pkg>.drvPath
   nix-build -A <pkg> --no-out-link
   # Rust only: proves nix-update can bump the vendor hash
   nix-instantiate --eval --strict --raw -A <pkg>.cargoDeps.vendorStaging.outputHash
   ```

5. Add the branch name to `nixpkgs-ci/branches.txt` on `master`.
6. `gh workflow run update.yml -R mtul0729/nixpkgs -f only=<branch>`, then confirm the
   package was built (the leg's log) and landed in the cache (see below).

### Fixing a failing package

`update` never leaves a broken commit on the branch: the build fails, nothing is
committed, and the run goes red. To iterate:

1. `jj workspace add ../fix-<name> -r 'pkg/<name>@origin'`
2. reproduce with `nix-build . -A <attr> --no-out-link` — same base as CI, so a local
   success is the derivation the runner would build
3. fix, then run the checks from *Adding a package* above plus `nixfmt`
4. push the branch
5. `gh workflow run update.yml -R mtul0729/nixpkgs -f only=pkg/<name> -f verify_only=true`
   runs the two checks without touching `nix-update` (~2-3 minutes)
6. `gh workflow run integrate.yml -R mtul0729/nixpkgs` publishes it into `integration`

Do not make a failing check pass by turning it off (`doCheck = false`, `--impure`, a local
override). If a package cannot build, leave the branch alone and say so.

## Why import-from-derivation is not allowed

nixpkgs forbids IFD, and `nixpkgs-review` enforces it by evaluating with
`--no-allow-import-from-derivation`. An attribute that trips it does not fail loudly:
`nix-eval-jobs` reports an error for that one attribute and `nixpkgs-review` drops it
from the list without a warning, exits 0, and the package is never built or cached. The
symptom is a package that silently never appears in the cache.

The usual cause in Rust packages is reading a lockfile out of the source derivation:

```nix
# IFD: readFile on a store path that has to be built first
cargoLock.lockFile = "${finalAttrs.src}/Cargo.lock";

# fine: one fixed-output derivation, hashed and substitutable
cargoHash = "sha256-...";
```

`cargoHash` is also what `nix-update` can bump on its own, since the vendor hash lives
in a real fixed-output derivation.

## Checking the cache

A green `update` or `integrate` run does not by itself mean a path is substitutable — a different
nixpkgs baseline produces a different derivation for the same package version. Ask the
cache directly:

```bash
nix-store -q --outputs $(nix-instantiate <pkg>) | while read -r p; do
  curl -sfI "https://mtul.cachix.org/$(basename "$p").narinfo" >/dev/null \
    && echo "$p cached" || echo "$p MISSING"
done
```

## Working on the fork locally

The repository is large (~4.4 GB of history), so do not clone it again for a second
working copy — add a jj workspace, which shares the object store:

```bash
jj workspace add ../nixpkgs-fork -r nixos-unstable@upstream
```

This sandbox caps address space at 4 GB, which is less than the repo, so heavy `jj` /
`git` operations have to run outside the cap:

```bash
systemd-run --user --quiet --pipe --wait --collect bash -c 'cd ../nixpkgs-fork && jj ...'
```

Editing and `nix build` are unaffected.

## Known sharp edges

- The CI commit's message is amended on every rebase, and the rebase step appends a fresh
  `[skip ci]` line each time — strip the old ones before appending, or the message grows
  one line per hour.
- Pushing `integration` needs `PUSH_TOKEN` (a PAT with `workflow` scope). `GITHUB_TOKEN`
  is rejected because the branch introduces workflow files.
- Shallow clones cannot be amended safely: `git commit --amend` in a depth-1 clone drops
  the parent and produces an unrelated history. Work through jj, or fetch enough depth.
- `nixpkgs` has its own `ci/` directory; personal files belong in `nixpkgs-ci/`.
- Upstream's `.gitignore` ignores `/AGENTS.md`. Ignore rules do not apply to tracked files, so the file is committed normally; the rule only means a freshly created copy has to be added with `jj file track --include-ignored` (or `git add -f`). This fork does not modify `.gitignore` for it.
- An `updateScript` with a `nix-shell` shebang (`#!nix-shell -p ...`) evaluates `import <nixpkgs>` **before** the script body runs. CI runners have no `NIX_PATH`, so such scripts need `-I nixpkgs=.` in the shebang (helix does this) or they fail without ever reaching the package logic.
