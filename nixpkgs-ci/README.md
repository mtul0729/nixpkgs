# The mtul0729/nixpkgs fork

This fork is, first, the home of the packages I maintain myself, and only second a
staging area for upstream pull requests. A branch here is a long-lived asset, not
something expected to disappear once a PR is merged.

## Shape

`master` is always based on upstream `nixos-unstable` and holds only CI files and
documentation — never package code. It may carry more than one commit; CI rebases the
whole stack onto the current `nixos-unstable` every hour. It contains only:

- `.github/workflows/{ci-check,update,integrate}.yml` — the only enabled workflows;
  every upstream workflow has been disabled by hand
- `nixpkgs-ci/` — the branch list and this document

Every package lives on its own topic branch, cut from upstream `nixos-unstable`, adding or
changing only `pkgs/by-name/<shard>/<name>/`. `integration` is generated by CI:
upstream `nixos-unstable` with each topic branch's effective diff squashed into one generated
commit. Consumers take a single input, `github:mtul0729/nixpkgs/integration`, so cache hits
are per-derivation and nothing has to be re-wired when a package is added. The branch only
advances after every attribute it carries has built, so a pin always names a cached rev.
The pin is a build handle rather than a version: it holds the system on one snapshot until the next
`nix flake update`, and once the branch is regenerated that rev belongs to no ref — it is
neither an archive nor a compatibility target.

Everything here is based on upstream `nixos-unstable` rather than `master`. The
systems consuming this fork run unstable, so `integration` sits on the same
commit the official binary cache was built against; basing it on `master` would
produce a second set of derivations for identical versions and miss every cache entry.

`nixpkgs-ci/branches.toml` is the single source of truth for which branches carry
packages. Adding a branch means editing that file; CI reads nothing else. TOML is
read by [`branches.py`](branches.py), which `ci-check`, `update` and `integrate`
all call, so the format has one definition instead of one `grep`/`sed` pipeline
per consumer.

## Model

Six objects, five invariants. The workflows implement the invariants; when a step looks
odd, find out which one it serves before changing it.

| object | written by | meaning |
| --- | --- | --- |
| `nixos-unstable` | upstream | the baseline every derivation is evaluated against |
| `pkg/<name>` | humans + `update` | a claim: this package, built on the baseline |
| candidate | one `update` leg | that branch rebased onto this run's `nixos-unstable`, carrying one update unit; invisible until it builds |
| update unit | `update` | every attribute one `nix-update` actually changed; built, committed and pushed as one |
| `integration` | `integrate` only | unstable with every branch squashed in; the published set of derivations |
| a consumer's `flake.lock` | the consumer | a build handle: one rev, therefore one closure |

1. **A branch tip is built.** A commit reachable on a `pkg/*` branch has had its whole
   unit built on the baseline it was verified against. No commit exists that only
   `integrate` has ever compiled.
2. **A unit is decided by evaluation.** Attributes that share a definition are grouped by
   what the evaluator reports changed — `drvPath` or `version` — never by directory or
   `updateScript` path. `siyuan` and `siyuan-preview` share both and still rotate
   different channels, so the path would merge packages that must stay apart.
3. **The cache is keyed by derivation.** Version numbers are not keys. A version, a hash,
   a dependency or the baseline commit all produce a new entry. That is why the baseline
   is `nixos-unstable` and not `master`, and why a rebuild after `integrate` is a cache
   miss rather than a mistake.
4. **`integration` is generated.** No human pushes it. Its fixed shape — upstream plus
   one squashed commit per branch — leaves every derivation outside the branches
   identical to upstream, so `cache.nixos.org` still applies to the rest of the system.
5. **A pin names a green `integration` rev.** `integrate` pushes the branch only after
   every attribute it carries has built, so following the branch can never land on a rev
   whose cache is still being filled. Moving `flake.lock` is still a deployment decision;
   it is just never a leap into a half-built tree.

Violating invariant 1 is what made `just switch` compile `magpie` locally on 2026-11-15:
`magpie` and `magpie-cli` read the same `version` line, so upgrading them one attribute
at a time built 4251 and then rewrote it to 4252; the tip carried a `magpie` that had
never been built, and only `integrate` compiled it. Invariant 2 is why the fix is a
derivation comparison and not a directory scan.

every job is based on it. The one remaining reason to look at upstream `master` is when
preparing a pull request against nixpkgs, to check whether a change already landed there.

## CI

Four workflows, each with one job:

| workflow | trigger | what it does |
| --- | --- | --- |
| `ci-check` | push to `master` touching `nixpkgs-ci/**` or `.github/workflows/**` | parses every workflow's YAML, validates `branches.toml`, and checks that each branch exists on the fork |
| `update` | hourly at `:13`, manual (`only`, `verify_only`) | per branch: `nix-update`, IFD check, build, and only then push the branch |
| `integrate` | after `update` finishes, manual | squash every branch onto current `nixos-unstable`, build the attributes the branches carry, then push `integration` |
| `build-branch` | manual (`branch`, `attrs`, `push_to_cache`) | build one branch's attributes without listing it in `branches.toml` — for evaluating a PR or trying a patch |

A docs-only push to `master` costs `ci-check` (~15 s) and nothing else.

### update

One matrix leg per branch. A leg builds a private `bot` candidate and does
**rebase → upgrade → verify → push** in the same worktree, so a branch never receives
a commit that has not been built:

1. fetch the branch and current `nixos-unstable`, find their merge base, and rebase the
   candidate onto the upstream tip. The merge base is also what identifies the packages
   the branch carries;
2. `nix-update -u <pkg> --format` — a package opts in by declaring `passthru.updateScript`.
   `--format` calls `nixfmt` out of `PATH`, which `nix-update` does not bring along, so
   the job installs `nixfmt-rs` next to it. `nix-update` fetches a release feed with a
   single unretried request, so a 502 or a dropped connection fails the leg outright; the
   step is retried three times, ten seconds apart, resetting to the pre-update tree between
   attempts because a failed run may already have rewritten `package.nix`. Only this step
   is retried — the build below is deterministic, and retrying it would burn CI time and
   hide a real failure;
3. re-evaluate every attribute the branch carries and treat the ones whose `drvPath`
   changed, plus the one that was updated, as a single unit. Two names can read the same
   definition: `magpie-cli` is `magpie.override { withGui = false; }`, and
   `siyuan-server` inherits the stable channel pin that `siyuan`'s update script writes.
   Updating such names one at a time leaves the tip unbuilt — the first leg built a
   version that the next `nix-update` then rewrote, and only `integrate` compiled the
   result. The grouping cannot come from the package directory or the `updateScript`
   path: `siyuan` and `siyuan-preview` share both yet rotate different channels, so the
   derivation is what decides;
4. `nix-instantiate --option allow-import-from-derivation false -A <pkg>.drvPath` for
   every attribute in the unit, the same IFD check `pkgs/README.md` asks for;
5. one `nix-build -A <a> -A <b>` for the whole unit inside `cachix watch-exec mtul`, so
   every result lands in the cache;
6. only then `git commit` (one commit per unit) and a force-with-lease push of the
   candidate.

#### Update frequency

Updates are scheduled per **update unit**: the attributes one `nix-update` run
rewrites together. A top-level `attrs` entry is a unit of its own; a
`[[branch.unit]]` table groups the attributes that share a definition and gives
the whole group one interval:

```toml
[[branch]]
name = "pkg/siyuan"
attrs = ["siyuan-preview"]

[[branch.unit]]
attrs = ["siyuan", "siyuan-server"]
interval = "6h"
```

`interval` defaults to `1h`, so a unit without one behaves like the hourly run.
The other accepted values are `2h`, `3h`, `4h`, `6h`, `8h`, `12h`, `daily`
(00:13 UTC) and `weekly` (Sunday 00:13 UTC). Slots are fixed on the UTC clock,
not measured from the previous check: `6h` means 00:13, 06:13, 12:13 and 18:13,
and a run delayed into a different UTC hour is evaluated as that hour. A single
attribute on its own cadence is a one-member `[[branch.unit]]`; top-level `attrs`
is only the shorthand for the hourly default.

The unit is the scheduling boundary, not the attribute. `siyuan` and
`siyuan-server` read the same stable-channel pin, and `magpie`/`magpie-cli` read
the same `version`; both pairs are one `[[branch.unit]]` in `branches.toml`.
`siyuan-preview` rotates a different channel, so it stays a separate hourly unit
in `attrs`. A `[[branch.unit]]` must list every attribute the update rewrites,
including ones by-name discovery would find anyway: an attribute that appears in
no unit is its own hourly unit, and throttling one half of a pair would let the
hourly half drag the other along. `branches.py validate` rejects an attribute
that appears twice, because two intervals for one definition have no meaning.

The gate applies only to `nix-update`. The rebase onto the current `nixos-unstable`, the
evaluation and the automatic baseline-conflict resolution still happen every hour,
because `integrate` merges the branches and a branch that stopped following its
baseline would be skipped there. A skipped or failed slot is retried at the next one,
not on the next hourly run, so `daily` can leave a package a day behind -- which is the
point of setting it.

An interval bounds when an update is *started*, not what a unit contains. If an hourly
unit's `nix-update` rewrites an attribute in a throttled unit, that attribute is still
built and published with the group, exactly as the derivation-based grouping requires.
`workflow_dispatch` ignores the schedule, so a manual run always checks every selected
attribute; `verify_only` is therefore unaffected.

The queue is per branch, not per workflow. One leg can run for well over an hour -- a
new version of a large Rust package has to be compiled from source on the runner, and no
binary cache has it yet -- and a workflow-wide group would hold every other package's
hourly update behind that leg. Legs of the same branch still run one at a time, and two
runs that reach the same branch are separated by the force-with-lease push.

The matrix restores one shared `.git` cache containing the complete upstream history,
not a `blob:none` partial clone. Checking out a partial clone has to fetch blobs for
roughly fifty thousand files on every leg even when no package changed; a complete cache
makes the checkout local and leaves only the new upstream blobs for the hourly fetch. The
cache key includes the UTC date because an `actions/cache` key is immutable: a static key
would stay at the first save forever and every run would replay the changes since then.
`restore-keys` carries the previous day forward, so only the first leg of a day uploads a
new complete cache. The `update` workflow is the only writer; `integrate` and
`build-branch` only restore it, because their filtered fetches must not turn the complete
cache back into a partial one. Measured on 2026-11-13: restoring the complete cache takes
about 28 s (3.2 GB at ~200 MB/s plus untar), after which fetch, checkout and evaluation
finish in about 10 s; a cold cache spends roughly 8 minutes on the same steps, so the
first leg after the UTC date rolls is the slow one, not a hang.

The measured runner has a 145 GB root disk (109 GB free) but only 16 GB of RAM and 3 GB
of swap. A large Rust package can peak in memory while linking 1161 crates: when it did,
the hosted runner was reclaimed and the log ended with `The runner has received a
shutdown signal` (exit 143) instead of a Nix error. Every leg of `update`, and
`build-branch` as well, therefore adds an 8 GB swapfile before installing Nix: the peak
belongs to the package, not to which workflow happened to build it.

Parallelism is not the lever it appears to be. Measured on 2026-11-13: a leg capped at
`--cores 3` sat at 3-6 GB resident while compiling and never touched swap, because the
spike comes from the final link, which is a single process that `-j` cannot stagger.
Capping the cores only made the leg slower, so builds use every core again and the
swapfile absorbs the link. A `[resmon]` line every ten seconds records memory, swap, the
largest resident process and free space. The link lasts a minute or two, so a per-minute
sample stepped right over it, and the process column tells a linker spike apart from the
compile phase.

The baseline is a build input, not a branch that has to follow `nixos-unstable` every
hour. There is no separate baseline updater: a successful package update carries the
baseline forward; otherwise the branch stays where it is. One case is automatic: a rebase
conflict caused by upstream bumping the same package, where upstream's side of the merge
base touched only `version`/`hash`/`rev`/`tag`-style lines and the branch tip carries a
newer version. The candidate takes the branch's `package.nix`, is verified like an update,
and only then is the new baseline pushed. Anything else -- upstream also changed
dependencies or build logic, the branch is not ahead, or the conflict is in another file
-- is left for a human. `integration` still gets today's baseline when it is regenerated.
When a package does update, the baseline move and the package change are verified and
pushed together.

A release-tag source that uses the default `nix-update-script` should pass its tag as
`rev = "v${version}"`, not `tag = ...`, while CI runs `nix-update` 1.16.0.
`fetchFromGitHub` records both `tag = "vX"` and `rev = "refs/tags/vX"`; 1.16.0 compares
`package.rev or package.tag` with the feed's `vX`, so the mismatch turns every no-op run
into a fake `vX -> vX` update and recomputes the source and dependency hashes.
`rev = "vX"` fetches the same archive contents and fixed-output path, but compares equal.
Upstream's unreleased `nix-update` reverses the preference; revisit this rule when the CI
pin moves.

If the build fails, nothing is committed. The leg pushes a
`ci-failed/<branch>/<pkg>/<content-hash>` tag; the hash covers the unit's versions and the
union of their definition directories' effective diffs from upstream, not the baseline
tree or another package's changes. A unit that is a single attribute digests
`version=<v>` exactly as before, so the format change did not invalidate existing tags; a
multi-attribute unit lists one `name=version` line per attribute. A later
`nixos-unstable` commit or an update to a sibling package therefore does not bypass the
tag, even when they share a data file. The same candidate is never retried
automatically: deleting the tag, changing the package, or choosing a different baseline
is a human decision. A new version or a package definition edit changes the hash and
forms a new candidate. A successful update deletes only that unit's failure tags, and the
tag lookup covers every attribute in the unit so a failure recorded under a sibling's
name is not retried either.

`-f only=pkg/helix` limits a run to those branches. `-f verify_only=true` still creates
and rebases the candidate, but skips `nix-update` and only runs the two checks: that is
the fast loop after a manual fix.

### Tests on `pkg/` branches

Packages on `pkg/` branches are built with `doCheck = false`. These branches exist to
produce a working package for this fork and its cache, not to stand in for upstream's
test matrix. Upstream suites often need a full desktop session, host filesystem features,
or tools that the Nix build sandbox deliberately does not provide.

This is not permission to hide a package build failure. The derivation, IFD check,
installation contents and runnable programs still have to pass. If a package is being
prepared for an upstream PR, run its tests and satisfy upstream's review requirements in
the separate PR branch; do not carry the fork's `doCheck = false` policy into that review
without explaining it.

#### Getting told when it stops

A leg that cannot move a package ends the step successfully with a `::warning::`, and
GitHub sends nothing for a green run — a failure buried in an hourly log went unnoticed
for nine hours once, so every path that stops a leg now opens an issue on the fork,
labelled `update-failed`: `nix-update` failed, a previous build failed and its
`ci-failed/` tag still stands, this build failed, or the push was rejected because the
branch moved. One issue per branch-and-package-and-reason, plus one branch-level issue for
a baseline rebase conflict that could not be auto-resolved; a repeat with the same summary
adds nothing, a change of version appends one comment. A successful candidate push closes
the package's issues and any baseline issue for the branch.

An issue is therefore a report about a failure that survived the retries, not about the
first dropped request. That distinction is the point of retrying in the first place: a
transient failure that never becomes an issue leaves nothing to close later.

### integrate

`integrate` squashes each branch's effective diff from its merge base into one generated
commit on the current `nixos-unstable`, in `branches.toml` order, runs `nix-build` for
the attributes those branches declare (top-level `attrs` plus every `[[branch.unit]]`'s
`attrs`, in addition to the by-name directory names), and pushes `integration` only
after every one of them built.

The source branches keep their full history. `integration` is a generated, force-pushed
artifact, so replaying every update commit there provides no consumer value: `pkg/magpie`
already spends minutes rebasing 134 update commits. The integration step instead uses
`git merge-tree --write-tree --merge-base` once per branch and creates one commit with
`git commit-tree`; the working tree is checked out only once at the end. A branch whose
effective diff conflicts with the integration built so far is skipped and named in a
warning; the step only fails when every branch was skipped, since then `integration` would
be plain `nixos-unstable`. The usual cause is a branch whose baseline has not caught up
with upstream yet, which `update` resolves on its next run. Fork refs are fetched with
`blob:none` and the fork is a promisor remote, so `merge-tree` and the final checkout
lazily fetch only the blobs they need. Fetching those refs without a filter makes Git
reconcile the upstream cache against the fork's complete trees and can spend minutes
transferring almost no data.

It has no schedule of its own: `update` runs hourly, so its completion is the signal,
and a second hourly cron only repeated the same integration work and build minutes later.
The cost is that a skipped or delayed `update` run delays `integration` by that much.

That build is still the drift check, but the gap it catches is usually much wider than the
few minutes between `update` and `integrate`. `nixos-unstable` advances in channel-sized
batches, so those two normally fetch the same tip. What does grow is the branch's baseline:
`update` does nothing for a package that is already at its newest version — no rebuild,
no baseline move — so the unstable a branch was last verified against can be days old.
`integrate` applies that branch's diff to the current unstable, and if anything in the
package's closure moved in the meantime its derivation changes and has to be built here;
otherwise the step is a pure download. The combined tree is also one that no single leg
ever built, so two branches can each pass and still change each other's derivations once
stacked. A failure turns the run red and leaves `integration` where it was: the branch
keeps the last rev whose attributes all built, and the next hourly cycle tries again. That
ordering is the point — it is what makes a consumer's pin name a rev that is already in
the cache instead of one that `integrate` is still compiling.

A branch that fails to merge is skipped and named in a warning; the others are still
published.
## Adding a package

1. Create a branch from upstream `nixos-unstable` and add `pkgs/by-name/<shard>/<name>/package.nix`.
2. Declare `passthru.updateScript` unless you want to pin it manually.
3. Make sure evaluation does not require import-from-derivation (see below).
4. Check it locally — these commands catch what CI would reject:

   ```bash
   nix-instantiate --eval --strict --option allow-import-from-derivation false -A <pkg>.drvPath
   nix-build -A <pkg> --no-out-link
   # Rust only: proves nix-update can bump the vendor hash
   nix-instantiate --eval --strict --raw -A <pkg>.cargoDeps.vendorStaging.outputHash
   ```

5. Add a `[[branch]]` table with the branch name to `nixpkgs-ci/branches.toml` on
   `master`; add `attrs` only for attributes by-name discovery cannot see. If several
   attributes share one definition, list them together in a `[[branch.unit]]` so they
   are updated and scheduled as one group.
6. `gh workflow run update.yml -R mtul0729/nixpkgs -f only=<branch>`, then confirm the
   package was built (the leg's log) and landed in the cache (see below).

### Fixing a failing package

`update` never leaves a broken commit on the branch: the build fails, nothing is
committed, and the leg reports an `update-failed` issue. To iterate:

1. `git fetch origin pkg/<name>`
2. `git worktree add ../fix-<name> -b fix/<name> origin/pkg/<name>`
3. fix, then run the checks from *Adding a package* above plus `nixfmt`
4. push `HEAD` to `pkg/<name>` with the `--force-with-lease` form from `AGENTS.md`
5. `gh workflow run update.yml -R mtul0729/nixpkgs -f only=pkg/<name> -f verify_only=true`
   rebuilds the candidate on current `nixos-unstable` and runs the two checks without
   touching `nix-update` (~2-3 minutes)
6. `gh workflow run integrate.yml -R mtul0729/nixpkgs` publishes it into `integration`

Do not make a failing build pass with `--impure` or a local override. If a package cannot
build, leave the branch alone and say so. `doCheck = false` is the deliberate fork policy
for `pkg/` branches (see *Tests on `pkg/` branches*), not a workaround for a build failure.

## Why import-from-derivation is not allowed

nixpkgs forbids IFD, and `nixpkgs-review` enforces it by evaluating with
`--no-allow-import-from-derivation`. An attribute that trips it does not fail loudly:
`nix-eval-jobs` reports an error for that one attribute and `nixpkgs-review` drops it
from the list without a warning, exits 0, and the package is never built or cached. The
symptom is a package that silently never appears in the cache.

The usual cause in Rust packages is reading a lockfile out of the source derivation:

```nix
# IFD: readFile on a store path that has to be built first
cargoLock.lockFile = "${finalAttrs.src}/Cargo.lock";

# fine: one fixed-output derivation, hashed and substitutable
cargoHash = "sha256-...";
```

`cargoHash` is also what `nix-update` can bump on its own, since the vendor hash lives
in a real fixed-output derivation.

## Checking the cache

A green `update` or `integrate` run does not by itself mean a path is substitutable — a different
nixpkgs baseline produces a different derivation for the same package version. Ask the
cache directly:

```bash
nix-store -q --outputs $(nix-instantiate <pkg>) | while read -r p; do
  curl -sfI "https://mtul.cachix.org/$(basename "$p").narinfo" >/dev/null \
    && echo "$p cached" || echo "$p MISSING"
done
```

## Working on the fork locally

The repository is large (~4.4 GB of history), so do not clone it again for a second
working copy — add a git worktree, which shares the object store:

```bash
git fetch upstream
git worktree add ../nixpkgs-fork -b <branch> upstream/nixos-unstable
```

This sandbox caps address space at 4 GB, which is less than the repo, so heavy `git`
operations have to run outside the cap:

```bash
systemd-run --user --quiet --pipe --wait --collect bash -c 'cd ../nixpkgs-fork && git ...'
```

Editing and `nix build` are unaffected.

## Known sharp edges

- The CI commit's message is amended on every rebase, and the rebase step appends a fresh
  `[skip ci]` line each time — strip the old ones before appending, or the message grows
  one line per hour.
- Pushing `integration` needs `PUSH_TOKEN` (a PAT with `workflow` scope). `GITHUB_TOKEN`
  is rejected because the branch introduces workflow files.
- Shallow clones cannot be amended safely: `git commit --amend` at a shallow boundary drops
  the parent and produces an unrelated history. This checkout was unshallowed on
  2026-11-12 and should stay that way; re-adding `--depth` recreates both that hazard and
  the costly boundary list that used to make every fetch look hung.
- `nixpkgs` has its own `ci/` directory; personal files belong in `nixpkgs-ci/`.
- Upstream's `.gitignore` ignores `/AGENTS.md`. Ignore rules do not apply to tracked files, so the file is committed normally; the rule only means a freshly created copy has to be added with `git add -f AGENTS.md`. This fork does not modify `.gitignore` for it.
- An `updateScript` with a `nix-shell` shebang (`#!nix-shell -p ...`) evaluates `import <nixpkgs>` **before** the script body runs. CI runners have no `NIX_PATH`, so such scripts need `-I nixpkgs=.` in the shebang (helix does this) or they fail without ever reaching the package logic.
